Application and ApplicationSet Finalizers

Short answer: can the finalizer be configured with an annotation?

✕ No — there is no annotation for this. Neither Application nor ApplicationSet supports an annotation that controls finalizer behavior. The finalizer is controlled exclusively by entries in .metadata.finalizers, plus the flags/fields that add or remove those entries.

Argo CD annotations such as argocd.argoproj.io/refresh, argocd.argoproj.io/manifest-generate-paths, argocd.argoproj.io/application-set-refresh or argocd.argoproj.io/compare-options have no effect on deletion / finalizer behavior.

Application finalizer

Finalizer values

The application-controller treats any of the following three .metadata.finalizers entries as a “cascade deletion” finalizer (see isPropagationPolicyFinalizer in pkg/apis/application/v1alpha1/types.go; constants in pkg/apis/application/v1alpha1/application_defaults.go):

FinalizerMeaning
resources-finalizer.argocd.argoproj.ioCascade delete; live resources are deleted with the foreground propagation policy (also the default the CLI/API applies when no explicit policy is given).
resources-finalizer.argocd.argoproj.io/foregroundCascade delete with the foreground propagation policy.
resources-finalizer.argocd.argoproj.io/backgroundCascade delete with the background propagation policy.

Helpers on the Application type

  • CascadedDeletion() — true if any of the above finalizers is present.
  • GetPropagationPolicy() — returns which finalizer is set.
  • SetCascadedDeletion(finalizer) / UnSetCascadedDeletion() — add/remove propagation-policy finalizers.
  • IsFinalizerPresent(finalizer) — checks for a specific finalizer.
Non-cascading delete If none of these finalizers is present, deleting the Application removes only the Application CR — live workload resources (Deployments, Services, …) are left orphaned.

Foreground vs. background

The only behavioral difference between the variants is the PropagationPolicy passed to the Kubernetes API when the controller deletes each managed live object (controller/appcontroller.go):

  • default / /foreground → DeletePropagationForeground
  • /background → DeletePropagationBackground

How the application-controller finalizes deletion

When an Application with a DeletionTimestamp still carries one of the finalizers, processAppQueueItem in controller/appcontroller.go calls finalizeApplicationDeletion:

  1. Resolve destination & project. If the destination cluster no longer exists (validDestination == false), live-object cleanup is skipped; the controller drops its cache entries and removes the finalizer so deletion can’t get stuck on a dangling cluster reference.
  2. List managed live objects (getPermittedAppLiveObjects). Objects already pending deletion make the controller wait (“N objects remaining for deletion”) and retry on subsequent reconciles.
  3. Delete each managed object with DeletePropagationForeground — or DeletePropagationBackground for the .../background variant.
  4. Clear cache & remove the finalizer (SetAppManagedResources, SetAppResourcesTree, then removeCascadeFinalizer → UnSetCascadedDeletion via merge patch). Removing the last finalizer lets Kubernetes GC finally remove the Application object.

Deletion errors surface as an ApplicationCondition of type DeletionError plus an audit event.

Setting and removing the Application finalizer

Argo CD CLI

  • argocd app delete APPNAME [--cascade] — adds the finalizer automatically, then deletes (the default).
  • argocd app delete APPNAME --cascade --propagation-policy background|foreground — selects the /background or /foreground variant (getPropagationPolicyFinalizer).
  • argocd app delete APPNAME --cascade=false — removes the finalizers first, so only the Application CR is deleted.
  • argocd app create … --set-finalizer — puts the finalizer on at creation time.

API & kubectl / GitOps

  • API: ApplicationService.Delete accepts cascade and propagationPolicy and patches .metadata.finalizers before deleting.
  • Declarative: declare the finalizer on the resource, then delete it: 
    metadata:
  finalizers: ["resources-finalizer.argocd.argoproj.io"]
# kubectl delete applications.argoproj.io APPNAME
    Omitting the finalizer means a non-cascading delete.

ApplicationSet finalizer behavior

Key fact The ApplicationSet CR itself has no Argo CD finalizer and no custom deletion handler: Reconcile returns immediately when the set carries a DeletionTimestamp. Generated Applications are removed purely by standard Kubernetes garbage collection via the ownerReference (controller reference) each one carries.
  • kubectl delete applicationset NAME → generated Application CRs are deleted via owner-reference cascading; each app’s own finalizer then decides whether its workloads go too.
  • kubectl delete applicationset NAME --cascade=orphan → keeps the generated Application CRs (and workloads).
  • Deleting the ApplicationSet never deletes anything directly — the applicationset-controller is not involved in that path.

Finalizers on generated Applications

  1. If spec.template.metadata.finalizers declares finalizers, they are copied verbatim onto every generated Application (getTempApplication) and kept in sync — manual edits on a generated app are reverted on the next reconcile.
  2. Otherwise RenderTemplateParams injects the default resources-finalizer.argocd.argoproj.io unless spec.syncPolicy.preserveResourcesOnDeletion: true, in which case generated apps get no finalizer (later deletions are non-cascading).

Pruning of generated Applications

When generator output changes, deleteInCluster issues a plain Delete; the finalizer already on the Application governs workload deletion. Special case: removeFinalizerOnInvalidDestination strips the resources-finalizer.argocd.argoproj.io finalizer (only that exact value) before deletion if the destination no longer matches a known cluster, so pruning can’t get stuck behind an un-honorable finalizer (issue #5817).

Troubleshooting stuck deletions

If an Application stays in Terminating, it is almost always the cascade finalizer waiting on live objects (or an unreachable cluster):

  • Fix or remove the blocking live resources and let the controller finish.
  • Drop the cascade requirement by removing the finalizer (workloads are then orphaned, not deleted): 
    kubectl patch app APPNAME -p '{"metadata":{"finalizers":[]}}' --type merge
  • For pruned ApplicationSet children pointing at deleted clusters, the controller already strips the finalizer automatically; if an app still hangs, check the same live-object causes.
